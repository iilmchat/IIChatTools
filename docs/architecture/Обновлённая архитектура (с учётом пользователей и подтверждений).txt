1. Обновлённая архитектура (с учётом пользователей и подтверждений)
1.1. Компоненты
Аутентификация / Авторизация: ASP.NET Core Identity (MSSQL) с ролями User и Admin.
Первый зарегистрированный пользователь автоматически получает роль Admin.

Веб-интерфейс:

HTML-страницы с Pure JavaScript (без фреймворков).

Страницы: / (главная админка), /status (статус сервера и статистика), /test (тестирование эндпоинтов).

Также будет API для получения данных для этих страниц.

API-контроллеры:

AuthController – регистрация, логин, получение JWT.

ToolsController – выполнение инструментов (с обязательной проверкой прав и ожиданием подтверждения для критичных действий).

ApprovalsController – получение списка ожидающих подтверждения, утверждение/отклонение.

AdminController – управление конфигурацией (чтение/запись настроек, управление пользователями).

StatusController – статистика, состояние системы.

Сервис подтверждений (IApprovalService):

Хранит в БД запросы на подтверждение (PendingAction):

Id, UserId, ToolName, Parameters, CreatedAt, Status (Pending, Approved, Rejected), ExpiresAt.

При вызове инструмента, помеченного как требующего подтверждения, вместо выполнения создаётся запись PendingAction и возвращается { requiresApproval: true, actionId: ... }.

Клиент (или сам сервер) может опрашивать /api/approvals/pending для получения списка.

Подтверждение действий ассистента:

Все действия, инициируемые LLM (через Tools API), по умолчанию требуют подтверждения пользователя.

Администратор может в настройках указать список инструментов, которые выполняются без подтверждения (белый список).

Это реализуется через атрибут [RequiresApproval] или через конфигурацию инструментов в БД.

Конфигурация в БД:

Таблица AppSettings (ключ-значение, тип, категория).

При старте загружаются настройки по умолчанию (из appsettings.json), затем перезаписываются значениями из БД.

Администратор может изменять настройки через админку (обновление БД).

Строка подключения к БД – только в appsettings.json / переменных окружения (не в БД).

Расширяемость:

Паттерн Strategy для инструментов: каждый инструмент – отдельный класс, реализующий ITool.

Добавление нового инструмента – просто создать класс и зарегистрировать его в DI.

Для добавления новых страниц – просто создать новый контроллер и представление.

1.2. Схема данных (дополнительные сущности)
ApplicationUser (IdentityUser) + доп. поля (например, IsActive).

AppSetting (Key, Value, Type, Category, IsDefault).

PendingAction (Id, UserId, ToolName, ParametersJson, Status, CreatedAt, ExpiresAt, ApprovedByUserId, ApprovedAt).

AuditLog (как ранее, но теперь с UserId).

AgentState – сохранение сессий суб-агентов (связь с пользователем).

MemoryEntry – долговременная память (принадлежит пользователю).

2. Технические решения (требуют вашего подтверждения)
2.1. Связь клиент ↔ сервер для подтверждений
Вариант А (Polling): Клиент периодически (каждые 5 сек) опрашивает /api/approvals/pending.

Вариант Б (SignalR): Реализовать SignalR хаб для мгновенных уведомлений о новых действиях.
Мой выбор: Предлагаю SignalR, т.к. это даёт лучший UX и снижает нагрузку. Но если вы против, сделаем Polling. Укажите ваш вариант.

2.2. Клиентский интерфейс (Pure JS)
Будут использоваться Fetch API для вызовов.

Для страниц можно использовать шаблонизацию на клиенте (например, простые innerHTML).

Страница /test – будет содержать форму для вызова любого инструмента с параметрами (для отладки).

Страница /status – отображать количество пользователей, выполненных действий, статус зависимостей, uptime.

Страница /admin – управление настройками, пользователями, просмотр логов (аудита).
Вопрос: Нужна ли сложная админка с пагинацией и фильтрацией, или минимальная?

2.3. Подтверждение действий (пользовательский опыт)
Когда LLM вызывает инструмент, требующий подтверждения, сервер возвращает { requiresApproval: true, actionId: "..." }.

Клиент (веб-интерфейс) должен отобразить модальное окно с описанием действия и кнопками «Подтвердить» / «Отклонить».

После подтверждения сервер выполняет действие и возвращает результат.

Важно: Для асинхронного ожидания, клиент может использовать долгий опрос или WebSocket (SignalR) для получения результата.

2.4. Роли и права
User: может использовать инструменты, но не может управлять настройками и пользователями.

Admin: полный доступ, может изменять конфигурацию, управлять пользователями, просматривать аудит.

Первый регистрирующийся пользователь автоматически становится администратором (это можно сделать в OnModelCreating или через Seed).

2.5. Хранение конфигурации
При старте приложения загружаем настройки из appsettings.json как baseline.

Затем читаем из БД таблицу AppSettings и перезаписываем значения (если есть).

При изменении через админку – обновляем запись в БД и перезагружаем конфигурацию в памяти (используем IOptionsSnapshot или собственный IConfiguration reload).

Итерация 1 (базовый фреймворк) – 3 дня:

Создание решения, проектов, добавление NuGet пакетов (Identity, EF, SignalR).

Реализация AppDbContext с Identity, миграции.

Настройка аутентификации (JWT) и регистрации.

Реализация DependencyChecker и AuditService (без привязки к пользователю пока).

Итерация 2 (пользователи и роли) – 2 дня:

Seed первого администратора.

Контроллеры AuthController (регистрация, логин).

Добавление UserId в AuditLog.

Итерация 3 (система подтверждений) – 3 дня:

Сущность PendingAction.

ApprovalService и ApprovalsController.

Интеграция в ToolsController: проверка, требование подтверждения.

Итерация 4 (веб-интерфейс) – 4 дня:

Разработка страниц: /, /status, /test, /admin.

Реализация логики подтверждения через модальные окна.

Интеграция SignalR для уведомлений.

Итерация 5 (инструменты) – параллельно с итерацией 4 – реализация всех инструментов (ФС, выполнение кода, веб, Git, суб-агенты).

Итерация 6 (конфигурация в БД) – 2 дня:

Сущность AppSetting, синхронизация с appsettings.json.

Админка для управления настройками.

Итерация 7 (финальная отладка, документация) – 3 дня.
